# ADR 0001：20ms PCM 块

- 状态：已采纳
- 日期：2026-10-23

## 背景

浏览器端要做多设备同步，必须把连续音频切成离散块，再按绝对时间戳排程播放。块大小同时影响：

- 排程精度（块越小，时间线越细）；
- 包开销（每块一个二进制帧 + 一个 JSON 帧）；
- 浏览器 `AudioBufferSourceNode` 的调度成本；
- 与 WebRTC/Opus 的复用难度（Opus 常用 20ms 帧）。

## 备选方案

| 块大小 | 每秒块数 | 对齐粒度 | 开销 |
|---|---|---|---|
| 10ms | 100 | 10ms | 双倍包量、调度更频繁 |
| 20ms | 50 | 20ms | 1.4Mbps PCM，1764 字节/块 |
| 40ms | 25 | 40ms | 包更少，但迟到一块的听感更明显 |

## 决定

固定 **20ms**：44100Hz × 0.02s × 1ch × 2B = **1764 字节**。

理由：

1. 与 Opus 的 20ms 帧对齐，WebRTC 出口可以直接复用同一份 PCM；
2. 50 块/秒对 WebSocket 和事件循环都很轻；
3. 排程粒度 20ms 已明显小于人耳可感知的跨设备回声阈值（约 20–30ms），再细收益有限；
4. JSON 元数据 50 条/秒的带宽可以忽略。

## 后果

- 跨设备对齐的理论下限是 20ms 量级，实际靠 `scheduledTime` 和时钟同步做到毫秒级；
- 迟到/丢块会以 20ms 为单位被感知，客户端必须做自适应抖动缓冲；
- 如果未来要压到 10ms，需要同时改协议、Opus 帧长和客户端缓冲策略。
